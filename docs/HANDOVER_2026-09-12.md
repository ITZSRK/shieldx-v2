## 1. The lane, and the deploy risk

This is the **public website repo** — `queloshieldx.in`, S3 + CloudFront +
Route 53.

`main` still deploys straight to production: `.github/workflows/deploy.yml`
triggers on `push: branches: [main]`, runs
`aws s3 sync dist/ s3://shieldx-v2-site/ --delete`, then invalidates
CloudFront `/*`. **Treat every merge to `main` as a production release.**

**This file originally reported `main` as completely unprotected** — the
protection API returned `404 "Branch not protected"`, so any push, including a
force-push, was a live deploy with no gate. SRK approved a fix and the HQ
session applied it. **Verified 2026-09-15:**

| Setting | Value |
|---|---|
| Pull request required | **yes** |
| Required approving reviews | **0** |
| Force pushes | **blocked** |
| Branch deletion | **blocked** |
| Required status checks | **none** |
| Enforce on admins | **no** (SRK keeps an override) |

Two settings look like gaps and are deliberate. **Zero required approvals** —
this is a one-person repo, so requiring an approval nobody can give would lock
SRK out of his own site. **No required status checks** — the secret scan
(`.github/workflows/secret-scan.yml`, added by PR #9) does **not run on pull
requests at all**, so requiring it would build a gate that can never pass.

> Do not "fix" either of these without first making the check actually run on
> `pull_request`. Requiring a check that never reports will wedge the repo.

The older compensating control still stands and is still only convention:
`CLAUDE.md` says build locally, screenshot, get SRK's approval before pushing.

## 4. Things tried that did not work, and why

Kept because each one cost real time to discover and the wrong fix looks
reasonable on paper.

**Nav breakpoint — two failed attempts before the right one.** Adding
Integration made six nav items, which overflow at 768px. First fix moved the
breakpoint `md` → `lg`; that produced a near-empty bar with a lone hamburger
across 900–1023px, visibly worse than the problem. Reverting to `md` after
dropping Integration was *also* wrong: measured, the five-item row **wraps
below 840px** — at 768 "How we deploy" breaks across three lines, the logo
collides with "Platform", the CTA overlaps "Company". That was true on `main`
too; `md` had never actually fit. Landed on a measured `min-[860px]`.
**Neither stock Tailwind breakpoint is correct for this nav.**

**Hero top padding.** `pt-20` (80px) exactly equals the fixed nav height, so
the eyebrow pill sat flush on the nav's bottom border with zero clearance.
`pt-28` gives 32px desktop / 44px mobile.

**Hero image: the textbook LCP fix made it worse.** The hero PNG is the LCP
element and was `loading="lazy"` — normally a bug. Setting it eager with
`fetchPriority="high"` pushed **LCP 4.9s → 6.2s and TBT 30ms → 100ms**,
because 239KB of PNG competes with the JS bundle on a throttled link. Reverted
to lazy; kept `width`/`height` (fixes CLS → 0) and `alt` (a11y 90→96, SEO
92→100). **The real fix is a WebP encode, ~210KB saved per Lighthouse** — not
attempted, because it is the only product imagery on the site and re-encoding
it is SRK's call.

**A Lighthouse run that reported a false 100.** Passing `--preset=desktop`
alongside mobile screen-emulation flags let the preset's *throttling* win while
`formFactor` stayed mobile. Reported Performance 100. Real mobile numbers are
**79–80**. Any future run must not mix a preset with manual emulation flags.

**Two rejected drafts of the homepage neutrality line.** "ShieldX never
operates collections" scoped the company to collections one screen after the
hero claims the credit lifecycle. The obvious repair — "never operates the
channels it scores" — is **factually false**: ShieldX runs a voice channel, and
Neutrality Charter commitment 2 says its own channels are scored by the
identical pipeline. SRK caught it. "Umpire, not player" was dropped for the
same reason — ShieldX *is* a player in the automated channels. Shipped wording
joins commitment 1 to commitment 2 and names the voice channel explicitly.

**A rebase that pushed mid-conflict.** Amending a commit in `pr-a` while `pr-b`
and `pr-c` were stacked on its old version caused a conflict, and `&&`
chaining pushed the branches while the rebase was unresolved. Recovered with
`git rebase --skip` on the superseded commit. The stack was re-verified linear
and in sync afterwards. **Do not chain `git push` after `git rebase` with
`&&`.**
